DriftGuard: a GitHub App that keeps DESIGN.md honest

A working-notes reference on how the app is built, why each piece is shaped the way it is, and where it goes next — written to be read once before a system-design interview and skimmed the day of.

Design system linter · GitHub App + Next.js + Supabase · monorepo with a shared @driftguard/linter package and a VS Code extension

01

Overview

What the product is, in one pass.

DriftGuard (package name designmd) enforces a repo's DESIGN.md — a markdown file with a YAML front-matter block describing colors, typography, spacing, and component tokens — on every pull request. It ships three surfaces that all share one core:

  • a GitHub App (Next.js on Vercel) that lints DESIGN.md on every PR, posts a findings comment, and sets a commit status;
  • a VS Code extension that runs the same lint rules live, as you type;
  • a dashboard (Supabase-backed) showing connected repos and recent PR check history.

The interesting engineering problem isn't parsing YAML — it's that DriftGuard checks two things at once: is DESIGN.md internally well-formed (valid references, WCAG contrast, required sections), and does it still match the CSS custom properties actually shipped in the codebase. That second check is the drift the name refers to.

02

Why it matters

The problem this is actually solving, and why it's timely.

AI coding agents (Cursor, Copilot, Claude Code) generate UI code fast, but they invent design decisions — a slightly different blue, an off-scale spacing value — whenever they aren't given a source of truth to read. DESIGN.md is a bet that the source of truth agents will actually respect is a markdown file sitting in the repo root, because that's exactly the kind of file agents already read by convention.

A file that nobody enforces just decays. Someone tweaks a CSS variable during a rushed PR and never updates the spec; six months later the spec describes a design system the product no longer has, and the AI agents that were supposed to be reading it are now reading something wrong with total confidence. DriftGuard is CI for that file — the same category of tool as ESLint or a type checker, except the "type" being checked is brand identity rather than code shape.

Framing for an interview

"It's a drift detector between two sources of truth that are supposed to agree — a declared spec and a shipped implementation — which is the same shape of problem as schema drift, infra drift, or contract testing between a client and server. I happened to apply it to design tokens."

03

Architecture

An npm-workspaces monorepo with one shared core and three thin adapters around it.

apps/

Next.js 14 App Router — src/app

  • Marketing site + GitHub OAuth login (via Supabase)
  • Dashboard (React Server Component reading Supabase)
  • /api/github/webhook — the core route
  • /api/auth/login, /auth/callback
  • Deployed on Vercel as serverless functions
packages/linter

@driftguard/linter — shared core

  • Pure functions: no filesystem, no network
  • parseDesignMd, lintDesignMd
  • Token canonicalization + CSS cross-validation
  • Consumed by both the webhook handler and the VS Code extension — one rule engine, not two
extension/

VS Code extension

  • Thin adapter: LintFinding → vscode.Diagnostic
  • Debounced on-type linting (300ms default)
  • Same rule engine as the webhook — findings you see locally are exactly what CI will report

External integrations sit around that core: GitHub via @octokit/rest and @octokit/auth-app (installation-scoped tokens, not a static PAT), Supabase for Postgres + Auth + Row Level Security, and Vercel for hosting. Two dependencies are already installed but not yet wired up — @anthropic-ai/sdk and stripe — see Expansion roadmap.

The branching logic that decides the outcome

Three distinct paths, each producing a different comment and commit-status state:

Product decision

Errors don't block merges by default — monitoredRepo?.block_on_error has to be explicitly true. Advisory-by-default reduces adoption friction for a team's first week using the tool; blocking is opt-in once they trust the signal.

Known gap

logPrCheck runs last. If the handler throws partway through, GitHub gets a 500 (and retries), but no row is written to pr_checks — there's no durable queue or dead-letter path yet, so a failed run leaves no audit trail. Worth naming unprompted in an interview; see roadmap #6.

06

Auth flow — and the PKCE detour

The one place a "correct" default had to be abandoned for a concrete, reproducible failure.

1
/api/auth/login
Route handler calls Supabase directly with flowType: 'implicit', gets the GitHub OAuth URL, redirects.
→
2
GitHub → Supabase
User authorizes; Supabase completes the OAuth exchange on its own domain.
→
3
/auth/callback
Client page parses #access_token straight out of the URL hash — no server round trip.
→
4
setSession()
Browser Supabase client stores the session in cookies via @supabase/ssr.
→
5
Dashboard
Middleware refreshes the session cookie on every request after this.

The first implementation used createServerClient with PKCE — the modern, recommended default. It kept failing: the code_verifier cookie set before the redirect to GitHub wasn't surviving the trip back from supabase.co to the vercel.app domain. That's a cross-site cookie problem (SameSite behavior), and it didn't matter which storage mechanism carried the verifier — route handler, server action, browser client — it was lost on every attempt.

The fix: switch to Supabase's implicit flow, which returns the access token directly in the URL fragment instead of an exchange code, so there's no verifier cookie to lose in the first place.

Trade-off, stated plainly

Implicit flow is generally considered less secure than PKCE — the token briefly lives in the URL fragment and browser history. It was the pragmatic fix for a real, reproduced cross-domain cookie failure, not a default choice. A cleaner long-term fix would be putting Supabase auth behind a same-site custom domain so the verifier cookie never has to cross origins.

07

Design patterns in play

Named less for the pattern-catalog label, more for the problem each one is actually solving here.

Canonicalize, then diff

Both DESIGN.md tokens and CSS :root variables get normalized into one shared CanonicalToken shape (extractCanonicalTokensFromDesignSystem / …FromCssVariables) — same fields, same hex normalization — before comparison. This is the general technique behind most config-drift and schema-drift tooling: don't write N×M comparison logic between two formats, write two adapters into one shape and diff that.

packages/linter/src/token-validation.ts 
// design token path → plausible CSS variable name(s), tried in order
function designTokenToCssVarCandidates(path: string): string[] {
  const [group, ...rest] = path.split(".");
  if (group === "colors") return [toKebab(rest.join("-"))];
  if (group === "spacing") return [`spacing-${toKebab(rest.join("-"))}`];
  if (group === "rounded") return [`rounded-${tail}`, `radius-${tail}`]; // try both
  return [toKebab(path.replace(/\./g, "-"))];
}

Naming conventions between a YAML spec and a CSS file are never guaranteed to line up exactly, so the matcher tries several plausible candidates rather than demanding one rigid mapping — heuristic matching over an exact contract.

Rule list, not a plugin registry

lintDesignMd is a sequence of independent addFinding(...) calls appended to one array — not a formal rule-plugin system with a registry and lifecycle hooks. With roughly a dozen fixed rules, a registry would be speculative generality; a straight-line function is easier to read top to bottom and just as easy to extend by adding one more check.

Idempotency at every integration boundary

Webhooks redeliver. Every handler that touches external state is written to be safely re-run:

  • upsertMonitoredRepo checks for an existing row by repo_id before inserting
  • PR comments are found via a hidden marker (<!-- designmd-bot -->) and updated in place instead of reposted — the same idiom Renovate and Dependabot use to avoid spamming a PR thread
  • Commit status is just re-set on every delivery — status updates are naturally idempotent

Two Supabase clients, two trust levels

User-facing reads (the dashboard) go through createServerSupabaseClient, which is cookie-scoped and respects Row Level Security. Server-only code (the webhook) goes through createServiceClient, which uses the service-role key and bypasses RLS entirely. The service-role client is never constructed anywhere that runs in the browser — the standard Supabase boundary for "trusted server code" vs. "authenticated user."

Fail open on incomplete config

Right after a fresh install, a PR can arrive before the monitored_repos row exists. getMonitoredRepo can return null, and the check still runs — it just can't block the merge (block_on_error defaults to off in that case). The tool chooses "always give feedback" over "only work if perfectly configured."

Line-accurate findings without a source-mapping YAML parser

js-yaml gives back parsed values, not line numbers. findYamlLine re-walks the raw YAML text separately, matching each finding's dot-path against indentation depth (assuming 2-space indent) to recover a line number — needed so VS Code can underline the right line and GitHub comments can deep-link to it.

WCAG contrast, by hand

Relative luminance (sRGB gamma correction) and the contrast-ratio formula are implemented directly rather than pulled in as a dependency — small enough, and self-contained enough, to just write:

packages/linter/src/linter.ts 
function contrastRatio(bg: string, fg: string): number | null {
  const l1 = hexToLuminance(bg), l2 = hexToLuminance(fg);
  const lighter = Math.max(l1, l2), darker = Math.min(l1, l2);
  return (lighter + 0.05) / (darker + 0.05); // WCAG AA threshold: 4.5
}

Data model

Four tables, one loose join.

profiles
  • id uuid → auth.users
  • email, github_username
  • plan: free · pro · team · enterprise
  • stripe_customer_id
github_installations
  • id bigint (GitHub's installation id)
  • user_id — github login, joined loosely to profiles.github_username
  • account_login, account_type, suspended
monitored_repos
  • id uuid
  • installation_id → github_installations, cascade delete
  • repo_full_name (unique), repo_id (unique)
  • enabled, block_on_error
pr_checks
  • id uuid
  • repo_full_name — matched by string, no FK
  • pr_number, sha, branch
  • status: passed · warned · failed · no_file
  • errors, warnings, checked_at

pr_checks joins to monitored_repos by repo_full_name rather than a foreign key — looser coupling, but it means a repo rename silently orphans historical check rows instead of failing loudly. profiles is the only table with a real RLS policy scoped to auth.uid(); the other three rely entirely on being accessed only through the service-role client, which is the gap flagged in Decisions.

Interview cheat sheet

The questions this project actually invites, with the short version of each answer. Expand for the long version.

Walk me through what happens when someone opens a PR.

Signature verified → installation token fetched → pending status set → DESIGN.md pulled from the PR's head branch → parsed and linted structurally → cross-checked against the repo's actual CSS variables → comment upserted and commit status set concurrently → check result logged. Full breakdown in PR check — data flow.

How do you stop someone from spoofing a webhook?

Every request's raw body is HMAC-SHA256'd with the app's webhook secret and compared to the x-hub-signature-256 header using crypto.timingSafeEqual — a constant-time comparison so the check itself can't leak the secret through response-time differences. Anything that fails is rejected with 401 before the JSON is even parsed.

How do you avoid commenting twenty times on one PR?

Every bot comment carries a hidden HTML marker. Before posting, the handler searches existing comments for that marker and updates it in place if found, instead of creating a new one — the same idiom Dependabot and Renovate use.

Why two separate Supabase clients?

One is cookie-scoped and respects Row Level Security — used anywhere a real user is making the request (the dashboard). The other uses the service-role key and bypasses RLS entirely — used only in trusted server code like the webhook handler, and never constructed anywhere that could run in a browser.

Why implicit OAuth instead of PKCE?

PKCE was the first attempt and is the better default, but its code_verifier cookie didn't survive the redirect from Supabase's domain back to the app's Vercel domain, regardless of how it was stored. Implicit flow sidesteps that entirely by returning the token in the URL fragment instead of an exchange code — accepted as a deliberate trade-off, not a default. See Auth flow for the honest version of this trade-off.

What's the actual novel technical piece here?

Not the YAML parsing — it's reconciling two independent sources of truth (a declared spec and shipped CSS) by normalizing both into one canonical token shape and diffing them. That's the same core technique behind schema-drift and infra-drift tooling generally.

What's the biggest scaling risk right now?

The whole fetch → lint → comment sequence runs synchronously inside one Vercel serverless function invocation per webhook delivery. Fine at current volume; a repo with very large PR traffic or slow GitHub API responses could hit function timeouts. The fix is a queue plus a background worker, which would also solve the "failed handler leaves no audit row" gap.

Why does the linter live in its own package instead of just src/lib?

Because it has two real consumers with different runtimes — the Next.js webhook handler (Node, server) and the VS Code extension (Node, but a completely separate process and packaging pipeline). Keeping it dependency-free and side-effect-free is what makes it importable from both without dragging in Next.js or Octokit.
